## 3. Metrics

### A1. Clock consistency (no audio needed)

Two tabs on the **same machine** share one physical clock. If clock sync works, both must compute the same server time. The sync panel's **clock check value** (`offset - performance.timeOrigin`) must therefore be equal in both tabs.

**Procedure:** open two tabs within one minute of each other (so the system clock doesn't shift between page loads), join the same room, wait 10 s, read the value in both tabs 5 times.

| Setup | Threshold |
|---|---|
| Local server (`localhost`) | \|difference\| ≤ 1 ms |
| Deployed server | \|difference\| ≤ 3 ms |
| Deployed server, laptop with `netem` 150 ms ± 20 ms (see A6) | \|difference\| ≤ 5 ms |

### A2. Time to sync
From clicking **Join** to the sync panel showing "synced": **≤ 2 s** (deployed server, phone on mobile data). Measure 5 times, report the max.

### A3–A5. Audio synchronization (the main metric)

**What is measured:** the time difference between the same click coming out of different devices, the **audio spread**.

**Test track:** `eval/tracks/click-60s.wav`: 60 s, 44.1 kHz, a 2 ms click (1 kHz burst) at every whole second, and a higher click every 10 s for orientation. Generated by a script in `eval/tracks/`.

**Recording setup**
- All devices next to each other, speakers facing one microphone (laptop or phone voice recorder, WAV if possible).
- **Equal distance to the mic, within ±5 cm**: sound travels 34 cm per millisecond, so 34 cm of difference = 1 ms of error.
- Set **one device's local volume to ~50 %** so its clicks are recognizably quieter. That's how you tell which click belongs to which device.
- Note each device's `outputLatencyMs` and timestamp source from the sync panel.

**Analysis (Audacity)**
1. Zoom into each click pair, place labels at each click's onset (the start of the waveform rise).
2. Spread = later onset − earlier onset, for **20 consecutive clicks** (seconds 20–40 of the track, after the start has settled).
3. Report **median** and **max** spread, and which device was ahead.
   (An automated click-detection script is planned for week 6; for the PoC, manual is fine.)

| # | Scenario | Devices / networks | Threshold |
|---|---|---|---|
| A3 | Same network | 2 laptops on the same Wi-Fi, deployed server | median ≤ 20 ms, max ≤ 40 ms |
| A4 | **Different networks** (PoC criterion) | laptop on Wi-Fi + phone on **mobile data** | median ≤ 50 ms |
| A5 | Three devices | 2 laptops + phone | median ≤ 50 ms (max spread among all three) |

**After commands:** repeat the A3 measurement right **after** each of: pause→resume, seek, skip, and a late join (F17). Pass: same thresholds as A3. This shows commands don't degrade sync.

### A6. Network impairment (shows the lead time + filtering work)
On a Linux laptop (replace `wlan0` with your interface):
```bash
sudo tc qdisc add dev wlan0 root netem delay 150ms 20ms   # 150 ms ± 20 ms
# … run A1 and A3 with this laptop + another device …
sudo tc qdisc del dev wlan0 root                           # remove
```
**Pass:** commands still take effect at the same moment on both devices; A3 thresholds hold.

### A7. Baseline measurements (no threshold, for the report)
- **Naive mode** (`?naive=1`, if implemented): run A3 with naive mode → the "before" number.
- **Drift baseline:** run A3 at minute 1 and again at minute 10 of continuous playback (no drift correction yet) → shows how much drift week 5 has to fix.

## 4. PoC demo script (≈ 5 min)

1. Phone (mobile data) + laptop (Wi-Fi), both on the public URL.
2. Create room on the laptop, open the link on the phone.
3. Upload a song, press play: both start together.
4. Pause on the phone, resume on the laptop, seek.
5. Classmate joins mid-song from their own phone: late join in sync.
6. Show the sync panel: offset, RTT, and the measured A4 numbers on a slide.
