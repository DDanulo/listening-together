# Protocol specification — v1

This document is the **single source of truth** for all communication between the client and the server.
The TypeScript types (`client/src/protocol/types.ts`) and the Java records (`server/.../protocol/`) must match it.
To change the protocol, update this document **first**, then both implementations in the same merge request (see [§9](#9-changing-the-protocol)).

---

## 1. Conventions

| Topic | Rule |
|---|---|
| Transport | HTTP for rooms and files; one WebSocket per client for everything real-time |
| Encoding | WebSocket messages are UTF-8 JSON text frames, one message per frame. Every message has a `"type"` field |
| Field names | `camelCase` |
| Time unit | **Milliseconds**, as a JSON number (may be fractional, e.g. `1532.417`) |
| Server time | Server's **monotonic** clock: ms since the server process started (`System.nanoTime()`-based). Never wall-clock time. All `…At` fields and `t1`/`t2` use it |
| Client time | `performance.now()` in the browser. Client time is **never sent** except as `t0` in `ping`, which the server only echoes back |
| Track position | ms from the start of the track |
| IDs | Opaque strings generated by the server (`roomId`, `memberId`, `trackId`), except `clientId`, generated by the client |
| Unknown fields | Must be ignored (forward compatibility) |
| Unknown `type` | Server replies with `error` `BAD_MESSAGE`; client ignores it and logs a warning |

## 2. HTTP API

Base path: `/api`. Error responses use the body `{ "code": "...", "message": "..." }` with the codes from [§7](#7-errors).

### `POST /api/rooms` — create a room
Rate-limited per client IP (default: 10 rooms per 10 minutes) → `429 RATE_LIMITED`. When the server holds its maximum number of rooms → `503 SERVER_BUSY`.

Response `201`:
```json
{ "roomId": "k3x9qa" }
```
The shareable link is `https://<host>/r/<roomId>` (client route).

### `GET /api/rooms/{roomId}` — check a room exists
Response `200` `{ "roomId": "k3x9qa", "memberCount": 2 }` or `404` `ROOM_NOT_FOUND`.

### `POST /api/rooms/{roomId}/tracks` — upload a track
`multipart/form-data`:

| Part | Required | Description |
|---|---|---|
| `file` | yes | Audio file, max **50 MB**. The type is detected from the file's content (MP3, FLAC, Ogg, WAV, MP4/M4A, WebM); the name and the claimed `Content-Type` don't count |
| `durationMs` | yes | Track duration in ms, measured by the uploading client (it decodes the file anyway) |
| `title` | no | Display title; defaults to the file name without extension |
| `memberId` | yes | Uploader's `memberId` |

Response `201`: a [`Track`](#track) object. The server then broadcasts a [`queue`](#queue) message to the room.
Errors: `404 ROOM_NOT_FOUND`, `413 FILE_TOO_LARGE`, `415 UNSUPPORTED_MEDIA_TYPE`, `409 QUEUE_FULL` (default: 30 tracks per room), `507 STORAGE_FULL` (server storage quota reached), `429 RATE_LIMITED` (default: 60 uploads per 10 minutes per client IP), `400 BAD_REQUEST`.

### `GET /api/rooms/{roomId}/tracks/{trackId}/file` — download a track
Returns the raw file with `Content-Type` (the detected type), `Content-Length`, `Cache-Control: private, max-age=86400, immutable` (a track's file never changes), `X-Content-Type-Options: nosniff` and `Content-Disposition: attachment`, so a browser never renders an upload as a page. Removed tracks return `404 TRACK_NOT_FOUND`.

### Room lifetime
Rooms and their files live **in memory / temporary storage only**. A room is deleted, including its files, **10 minutes after its last member disconnects**, or 10 minutes after creation if nobody joins. A removed track's file is deleted immediately.

## 3. WebSocket connection

Endpoint: `GET /ws/rooms/{roomId}` (`wss://` in production).

If the room does not exist, the server sends `error` `ROOM_NOT_FOUND` and closes with code `4404`.

### 3.1 Session lifecycle

```
client                                            server
  │── (connect /ws/rooms/k3x9qa) ───────────────────►│
  │── hello {protocolVersion, clientId, name} ──────►│
  │◄──────────── welcome {memberId, room snapshot} ──│
  │── ping ×10 (clock-sync burst) ──────────────────►│
  │◄──────────────────────────────────── pong ×10  ──│
  │          … client can now schedule audio …       │
  │◄──── members / queue / playback (on change) ─────│
  │── ping every 5 s, stats every 2 s ──────────────►│
```

1. After connecting, the client sends `hello` **as its first message**, within **10 s** (otherwise close `4400`). The server ignores everything else until `hello` (replies `error` `BAD_MESSAGE`). A room holds at most **20 members**; a `hello` to a full room gets `error` `ROOM_FULL` and close `4409`.
2. The server replies `welcome` with the full room snapshot.
3. The client runs a clock-sync burst ([§4](#4-clock-synchronization)). It **must not start audio playback** before it has a clock estimate.
4. From then on, the server pushes `members`, `queue` and `playback` messages whenever they change.

### 3.2 Reconnection

- The client generates `clientId` (UUID v4) once per browser tab and keeps it in `sessionStorage`.
- On disconnect, the client reconnects with exponential backoff (0.5 s, 1 s, 2 s, 4 s, then every 8 s) and sends `hello` with the **same `clientId`**. The server maps it to the **same `memberId`**.
- **While disconnected, the client keeps playing** based on the last `playback` state and its last clock estimate. Audio is local, so a short disconnect must be inaudible.
- After reconnecting, the client runs a new ping burst and reconciles with the `playback` state from `welcome`.
- The server marks a member `connected: false` on disconnect and removes it after **60 s** without reconnecting.

### 3.3 Close codes

| Code | Meaning |
|---|---|
| `1000` | Normal close (user left) |
| `1001` | Server shutting down |
| `4400` | Protocol violation or unsupported `protocolVersion` |
| `4404` | Room not found |
| `4409` | Room is full |
| `4429` | Too many messages (rate limit) |

## 4. Clock synchronization

The client estimates the **offset** between its own clock and the server clock with an NTP-style exchange.

```
client sends ping at t0  ──►  server receives at t1
client receives at t3    ◄──  server replies at t2

rtt    = (t3 - t0) - (t2 - t1)
offset = ((t1 - t0) + (t2 - t3)) / 2          // serverTime ≈ clientTime + offset
```

### Messages
**`ping`** (client → server)
```json
{ "type": "ping", "seq": 17, "t0": 48211.305 }
```
**`pong`** (server → client)
```json
{ "type": "pong", "seq": 17, "t0": 48211.305, "t1": 902114.552, "t2": 902114.601 }
```

### Server requirements
- Take `t1` **as the first thing** when the message arrives, and `t2` **as the last thing** before sending.
- Answer `ping` immediately, before any other queued work for that session.
- Never rate-limit `ping` below 20 messages/s per client. The per-connection limit covers all message types together (default: bursts of 100, 20 messages/s sustained); exceeding it → `error` `RATE_LIMITED` and close `4429`.

### Client strategy (recommended, not part of the wire contract)
- On (re)connect: burst of **10 pings, 50 ms apart**.
- Afterwards: **3 pings every 5 s**.
- Keep a sliding window of recent samples. Use the offset from the samples with the **lowest `rtt`** (least affected by jitter).
- The offset formula assumes symmetric network delay; asymmetric routes cause an error of up to `rtt / 2`.

## 5. Playback model

The server holds **one authoritative playback state per room**. Clients never change playback locally; they send commands and wait for the server's new state.

### `PlaybackState`
```json
{
  "rev": 42,
  "status": "playing",
  "trackId": "t_8f2c",
  "position": 30000,
  "effectiveAt": 905120.0
}
```

| Field | Meaning |
|---|---|
| `rev` | Revision number, increases by 1 with every change. Clients **ignore states with `rev` ≤ the last applied one** |
| `status` | `"playing"`, `"paused"` or `"stopped"` (nothing to play) |
| `trackId` | Current track, or `null` when `stopped` |
| `position` | Track position (ms) **at server time `effectiveAt`** |
| `effectiveAt` | Server time at which this state takes effect |

### How clients apply a state
Let `T` be the current server time (`clientNow + offset`):

- **`playing`:** the expected track position is
  `expected(T) = position + (T - effectiveAt)`
  - If `effectiveAt` is in the future, schedule the start for exactly `effectiveAt` (Web Audio `start(when, offset)`).
  - If `effectiveAt` is already in the past (message arrived late, or late join), start **immediately** at `expected(now)`, slightly in the future to leave time for scheduling.
- **`paused`:** at `effectiveAt`, stop playback and keep `position`. Until then, keep playing.
- **`stopped`:** stop at `effectiveAt`.
- Until `effectiveAt`, the **previous state still applies**. A pause scheduled 1 s ahead means "keep playing for 1 s, then stop".

The output-latency correction (e.g. Bluetooth headphones) is applied locally by each client and is not part of the protocol.

### Lead time
The server schedules every change **`LEAD_MS` = 1000 ms** in the future (`effectiveAt = now + LEAD_MS`). This gives every client time to receive the message, even with high latency, and to prepare. The value is server configuration and may be tuned during evaluation.

### Auto-advance
When the current track ends, the server switches to the next track in the queue **without a gap**:
- `endAt = effectiveAt + (durationMs - position)`
- At `endAt - LEAD_MS`, the server broadcasts a new state: next track, `position: 0`, `effectiveAt: endAt`.
- If there is no next track: `status: "stopped"`, `effectiveAt: endAt`.

## 6. Message reference

### 6.1 Client → server

#### `hello`
```json
{ "type": "hello", "protocolVersion": 1, "clientId": "b1c4…", "name": "Danylo" }
```
`name`: 1–32 characters, trimmed.

#### `ping`
See [§4](#4-clock-synchronization).

#### `command`
Requests a playback change. The server answers by broadcasting `playback` to **all** members, sender included. The sender must **not** apply the change optimistically.

| `action` | Extra fields | Effect |
|---|---|---|
| `play` | — | Resume from the paused position; if `stopped`, start the first track in the queue. `INVALID_COMMAND` if already playing or the queue is empty |
| `pause` | — | Pause; `position` = expected position at the new `effectiveAt`. `INVALID_COMMAND` if not playing |
| `seek` | `position` | Jump within the current track; keeps `playing`/`paused` status. `INVALID_COMMAND` if `stopped` or `position` outside `[0, durationMs)` |
| `skip` | — | Play the next track in the queue from position 0, even if paused (`stopped` if there is none). `INVALID_COMMAND` if `stopped` |
| `select` | `trackId` | Play the given track from position 0 |
| `remove` | `trackId` | Remove a track from the queue. If it is playing, behaves like `skip` first |

```json
{ "type": "command", "action": "seek", "position": 95000 }
```
Concurrent commands are processed in the order they arrive; the last one wins. A new state's `effectiveAt` is never earlier than the current state's, so the server can compute positions from the current state alone.

#### `trackStatus`
Reports the download state of a track, so the UI can show who is ready.
```json
{ "type": "trackStatus", "trackId": "t_8f2c", "status": "ready" }
```
`status`: `"downloading"`, `"ready"` or `"error"`. The server **does not wait** for clients to be ready; a client that becomes ready late joins the playback in progress.

#### `stats`
Sync quality report, sent every **2 s** while connected. Used for the UI and logged by the server for evaluation.
```json
{ "type": "stats", "offsetMs": -1532.4, "rttMs": 38.2, "driftMs": 1.7, "outputLatencyMs": 12.0 }
```
| Field | Meaning |
|---|---|
| `offsetMs` | Current clock offset estimate |
| `rttMs` | RTT of the best recent ping sample |
| `driftMs` | `expected - actual` track position (positive = this client is behind); `null` when not playing |
| `outputLatencyMs` | Audio output latency used for correction; `null` if unknown |

### 6.2 Server → client

#### `welcome`
```json
{
  "type": "welcome",
  "protocolVersion": 1,
  "memberId": "m_2a",
  "serverTime": 902114.6,
  "room": {
    "roomId": "k3x9qa",
    "members": [ /* Member */ ],
    "queue":   [ /* Track */ ],
    "playback": { /* PlaybackState */ }
  }
}
```
`serverTime` is for information/debugging only. The clock offset must come from `ping`/`pong`.

#### `pong`
See [§4](#4-clock-synchronization).

#### `members`
Full list, sent when someone joins, leaves, reconnects or changes download status, and **at most every 2 s** for `sync` updates.
```json
{ "type": "members", "members": [ /* Member */ ] }
```

#### `queue`
Full queue in play order, sent on every change.
```json
{ "type": "queue", "tracks": [ /* Track */ ] }
```

#### `playback`
```json
{ "type": "playback", "state": { /* PlaybackState */ }, "cause": { "action": "pause", "memberId": "m_2a" } }
```
`cause` is `null` for server-initiated changes (auto-advance).

#### `error`
```json
{ "type": "error", "code": "INVALID_COMMAND", "message": "No track with id t_99", "ref": "command" }
```
`ref`: the `type` of the message that caused it, if any.

### 6.3 Shared objects

#### `Member`
```json
{
  "memberId": "m_2a",
  "name": "Danylo",
  "connected": true,
  "downloads": { "t_8f2c": "ready", "t_91aa": "downloading" },
  "sync": { "offsetMs": -1532.4, "rttMs": 38.2, "driftMs": 1.7 }
}
```
`sync` is `null` until the member has sent `stats`.

#### `Track`
```json
{
  "trackId": "t_8f2c",
  "title": "Song name",
  "durationMs": 214380,
  "sizeBytes": 5123456,
  "mimeType": "audio/mpeg",
  "uploadedBy": "m_2a",
  "url": "/api/rooms/k3x9qa/tracks/t_8f2c/file"
}
```

## 7. Errors

| Code | HTTP | Meaning |
|---|---|---|
| `ROOM_NOT_FOUND` | 404 | Room does not exist (WebSocket: close `4404`) |
| `TRACK_NOT_FOUND` | 404 | Unknown `trackId` |
| `BAD_MESSAGE` | — | Malformed JSON, unknown `type`, missing fields, or message before `hello` |
| `UNSUPPORTED_VERSION` | — | `protocolVersion` not supported (WebSocket: close `4400`) |
| `INVALID_COMMAND` | — | Command not valid in the current state (e.g. `seek` beyond track duration) |
| `FILE_TOO_LARGE` | 413 | Upload over 50 MB |
| `UNSUPPORTED_MEDIA_TYPE` | 415 | Upload is not `audio/*` |
| `BAD_REQUEST` | 400 | Other invalid HTTP request |
| `RATE_LIMITED` | 429 | Too many requests (HTTP) or messages (WebSocket: close `4429`) |
| `ROOM_FULL` | — | Room has the maximum number of members (WebSocket: close `4409`) |
| `QUEUE_FULL` | 409 | Room has the maximum number of tracks |
| `STORAGE_FULL` | 507 | Server storage quota reached |
| `SERVER_BUSY` | 503 | Server holds the maximum number of rooms |

## 8. Example: pause and resume

```
t (server)   event
──────────   ──────────────────────────────────────────────────────────────────
 900000      state rev 7: playing t_8f2c, position 0, effectiveAt 900000
 930000      Karol → command {action: "pause"}
 930000      server: effectiveAt = 930000 + 1000 = 931000
             position at 931000 = 0 + (931000 - 900000) = 31000
             broadcast playback rev 8: paused, position 31000, effectiveAt 931000
 930000–931000  all clients keep playing, and stop exactly at server time 931000
 945000      Danylo → command {action: "play"}
             broadcast playback rev 9: playing, position 31000, effectiveAt 946000
 946000      all clients resume at 31000 ms in the track
```

## 9. Changing the protocol

1. Edit this document first, in the same merge request as the code.
2. Update `client/src/protocol/types.ts` **and** the Java records in `server/src/main/java/pl/lodz/p/sina/listening/protocol/`.
3. Breaking changes (renaming/removing fields, changing semantics) bump `protocolVersion`.
4. Additive changes (new optional fields, new message types) don't need a version bump, because unknown fields and types are ignored.
